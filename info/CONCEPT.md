# Концепция проекта: игра «Киллер / Папарацци» как веб-сайт

## Что было до этого

Проект начинался как **Telegram-бот** игры «Киллер/Папарацци»: игроки в кругу, у каждого
цель — следующий; поймал (фото-пруф) → подтверждение → новая цель; последний выживший
побеждает. Есть админ-панель для управления жизненным циклом игры. Вся логика и весь UX
жили **в чате**: inline-меню, FSM-диалоги, показ цели через спойлер, разметка сообщений.

Затем возникла задача сделать игру **мультиплатформенной** (Telegram + VK, одна общая игра).
При анализе выяснилось: перенести чат-UX в VK дорого и хрупко — у VK нет форматирования и
спойлеров (а на спойлере держится показ цели), лимиты на кнопки, нельзя писать первым,
двухшаговая загрузка вложений, ограниченные FSM-диалоги. Обход этих ограничений — самая
затратная часть работы.

> **Важно (актуальная поправка):** старый проект `killer_game_tg_bot` мы **не трогаем**.
> Веб-версия пишется **с нуля как отдельный проект**, функционирующий **по аналогии** с ботом.
> Исходный бот используется только как **функциональный референс** — эталон поведения и
> исчерпывающий список фич. Полная инвентаризация команд, кнопок и use-case с условиями
> доступности вынесена в [`FEATURES.md`](FEATURES.md) — она и есть спецификация для порта.

## Актуальная постановка задачи

Сделать основной функционал игры в виде **разворачиваемого веб-сайта**, а Telegram и VK
свести к **тонким ботам-уведомителям**: они только присылают уведомления о событиях игры
и выдают ссылку для входа. Вся игровая логика, интерфейс игрока и админка живут на сайте.

**Согласованные решения:**
- весь функционал — на сайте;
- новую версию пишем **с чистого листа**, старый бот — только эталон поведения ([`FEATURES.md`](FEATURES.md));
- вход по «магической ссылке» из бота (одноразовый токен → session-cookie);
- хостинг на VPS с доменом и HTTPS;
- Python + серверный рендер (FastAPI + Jinja2), доменная логика пишется заново по мотивам бота.

## Идея (почему так лучше)

Перенос UX из чата в браузер **снимает почти все ограничения VK разом**:
- богатый интерфейс вместо ограниченных чат-меню и диалогов;
- показ цели — click-to-reveal через CSS (не нужен спойлер);
- фото-пруфы поимок — обычная загрузка файла;
- полноценная админка вместо цепочек команд;
- боты сводятся к тому, что **обе платформы делают одинаково хорошо** — отправке сообщений;
- добавить новый канал уведомлений (ещё одна сеть, e-mail и т.п.) становится тривиально.

## Целевая архитектура (кратко)

```
Браузер (игроки + админы)
   │ HTTPS, session-cookie
   ▼
FastAPI + Jinja2 (web/)
   ├── роуты игрока: статус, цель (reveal), «поймал» (фото), accept/deny, профиль, join
   ├── роуты админа: старт/пауза/сброс/итоги, управление игроками, broadcast, лог
   ├── auth: magic-token → session-cookie
   └── ЯДРО (пишется заново по мотивам бота): core/game.py, core/user.py, core/identity.py, db.py
   │
   └── registry.get(platform).send(...) ── уведомления ──►  тонкие боты TG / VK
   ▼
SQLite (WAL) → при росте PostgreSQL
```

Всё в одном процессе (uvicorn + бот-поллинги как asyncio-таски): веб и боты делят общий
`registry` и БД, поэтому кросс-платформенные уведомления «просто работают» (TG-игрок и
VK-игрок в одной игре получают уведомления каждый в своей сети). Модули `core/`, `registry`,
`identity` — это **новый код**, спроектированный по образцу бота, а не импорт из `killer_game_tg_bot`.

**Поток входа:** `/start` боту → бот создаёт одноразовый токен и шлёт ссылку
`https://<домен>/login?token=…` → клик ставит подписанную cookie и открывает дашборд.

## Что переносим по аналогии, а что не нужно

Старый бот не импортируется — весь код веб-версии новый. Но по функциям он делится так
(подробная карта с условиями доступа — в [`FEATURES.md`](FEATURES.md)):

**Воспроизводим (доменная логика и модель):** правила круга целей, join/leave, поимка с
accept/deny, очередь воскрешений, подсчёт итогов и топа, роли и админ-действия, канал
уведомлений (`registry`), идентичность и вход по ссылке (`identity`), WAL, тексты правил.

**Не нужно (специфика чат-бота):** `handlers/` (чат-команды), `menu/` (inline-меню),
`dialogs/` (FSM-диалоги), чат-разметка и спойлер цели, VK-рендер клавиатур — в браузере это
обычный HTML/CSS. Также уходят команды `/commands`, `/cancel`, рестарт/стоп из чата,
групповой TG-лог (см. раздел «что уходит» в [`FEATURES.md`](FEATURES.md)).

## Текущее состояние

В этой папке (`killer_game_web/`) собран стартовый каркас на FastAPI + Jinja2 (`app.py` +
`templates/index.html`) — динамический макет главного экрана (меню игрока и админа:
сообщение-«пузырь» + inline-кнопки, как в боте), данные пока захардкожены. Запуск — через
[`start.sh`](start.sh) (см. `README.md`).

Следующие шаги: написать игровое ядро и БД по спецификации [`FEATURES.md`](FEATURES.md),
вход по ссылке, живые действия игрока и админки, тонкие боты-уведомители, деплой на VPS.
